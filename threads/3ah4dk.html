ambient_solomon true purpose

▲ 48 ptsu/reozeJun 20, 201517 comments at captureOpen original on Reddit ↗
Documented under:Beat-Grid Tempo ForensicsLoop-Point Seam Forensics

For the TLDR version: If you show up at a certain security guard inside the movie studio, one of two different scripted conversations will start, which one determined completely at random. You will then be spawned on top of an Akuma. If you leave the mission area the script ends immediately.

To me it almost sounds as if Michael is to ride the Akuma within the movie studio somewhere (Stunts maybe?). There are no objective checks that I can see within the code at all. Which would mean they are most likely assigned during the conversation. I'm unsure how that works exactly.

Here is the extremely high level version of ambient_solomon
https://gist.github.com/anonymous/25892d5a18f226b03256

First off I'll say that I do not 100% understand this script as well as others. What I do have labeled I am pretty confident in. If I didn't feel confident then I placed a comment next to it instead.

There are also some errors, early on I accidently found and replaced "func_3" instead of "func_3(", causing functions 31-39 to also get replaced with "check_and_clear_flowlaunch_bit"+number. Consider these unknowns, I have not looked at them.

There were some who believed that solomon held a link to a 4th UFO simply because the coordinates for the two ambient_ufo's appear right below the coordinates used in the ambient_solomin script. People may recognize the coordinates below.

"mission_sphere_origin = {-1124.392f, -514.7001f, 33.21493f};"
"mission_sphere_radius = 200f;"
"hippy_camp_ufo_position = {2490f, 3777f, 2402.879f};"
"army_base_ufo_position = {-2052f, 3237f, 1450.078f};"

Unfortunately these coordinates do not relate to each other at all. "mission_sphere_position" and radius exist simply to allow this script to pass it's first logic check into the more complex sections of the script. Most scripts have these checks in order to reduce overhead on the actual script machine.

"if (is_entity_alive(player_ped_id()))"
"{"
" while (bVar0 == 0)"
" {"
" bVar0 = ((get_mission_flag() == 0 && get_current_ped() == 0) && is_entity_in_sphere(player_ped_id(), mission_sphere_origin, mission_sphere_radius));"
" check_exit_conditions();"
" }"
"}"

Essentially what this is saying is, IF we are NOT on a mission (==0) AND the current_ped == MICHAEL (0) AND the current ped is within the sphere defined above. Proceed through the script. Otherwise, check if the script should be terminated.

The good stuff actually in run_solomon_state_machine, unfortunately while I mapped out 95% of it's function the 5% that I don't know is where the real meat is. A state machine has a number of different states. Consider each step a state. In this machine it only moves forward (Step 1 to step 2) simplifying things. It goes something like this.
For the most part, each of these steps continues it's checks until it passes or the player leaves a specified zone.

Keep in mind, these steps are not "steps" for the player. They are steps within the script, these should all happen fluidly without player intervention once the script is triggered correctly

Step 1: If the player is in a specific area (start : -1210.236f, -579.875f, 26.33215f, End: -1204.725f, -586.3573f, 29.56773f, AngleBetween: 6 Radians) Or the players vehicle is in a very similar area, and the player is looking in a specific direction (I imagine the guard booth) move on to Step 2.

Step 2: Force the player to stand still, or the vehicle to stop. If the security guard is within 5 "units" of a specific point (-1210.152f, -578.0859f, 26.7238f) set michael as a scripted conversation target. Then it runs "func_41()" (I apologize I forgot to name this). This is a purely random check. If it passes, it starts the conversation "AMSOL_HERE", otherwise it starts the conversation "AMSOL_WORK". The return result of the start_conversation function determines whether or not we moved to Step 3. This may or may not depend on which conversation was started.

Unfortunately, this is where I can't quite seem to decipher what happens to an exact T. So I cannot confidently say what goes on. What I can say though, is that by the end of the function it does definitely END a scripted conversation.

Step 3: Try to stop the players vehicle again.

Step 4: Clear player "tasks"

Step 5: Reopen movie studio (it gets closed at the beginning of the script).

Step 6: "generate_mission_akuma". What this function does is create a new Akuma at the position passed into the function and then places the player on top of it. One thing to note is that this function also calls "set_blocking_of_non_temporary_events" which implies that during this script, other events ambient and random events will not fire.

Step 7: This consists solely of the following check

 "if (!is_entity_aabb_in_angled_area(player_ped_id(), -1055.514f, -474.6371f, 35.6278f, -1051.23f, -464.4126f, 39.91479f, 9.5f))"

This is almost identical to the first check that the script does with slightly different coordinates. It also takes into account the entire bounding box of the player and it's vehicle instead of just the location which is why the function is different.

When this check fails, we move on to "step 8"

Step 8: Cleanup - Delete akuma, security guard, and terminate the ambient_solomon script.

Knowing all of this, I actually pose everyone a question. Does any of this sound familiar to you? It does not to me.

I fully understand that what I showed are my own named functions, and while I cannot guarantee the validity of those names. I implore you to look at the code yourself and correct me if I'm wrong. It is supplied in the link above. If there are any corrections feel free to post them here or PM me and I can reevaluate this entire post.
